Flipper Zero app · Continental / VDO TG1C sensors

Wake a tyre sensor that is still in shipping mode

A replacement tyre pressure sensor can arrive asleep. The car never hears it, so one wheel stays blank on the dashboard. Garages fix this with a dedicated TPMS tool. This project does it with a Flipper Zero.

On 12 November 2026 one short command from a Flipper, held at the tyre valve of a Jaguar XF, changed the stuck sensor's status to the value the car's three working sensors report. On the next drive the dashboard showed that wheel.

Confirmed by the car · 12 November 2026

After the command the sensor reported the same status as the working sensors and took up their listening rhythm. On the drive that followed the dashboard showed a pressure for all four wheels (35, 35, 35 and 36 psi) and the car's own test status read OK for all four sensors. Before the command the car logged "no signal" for that wheel.

One car and one sensor. It has kept working since, through driving and parking (the owner's report, 23 November 2026). The app described here is TPMSFlipper 1.0.0, the first public build. It has passed its tests on a computer with a simulated sensor and has not yet run on a Flipper. The last development build, the same code under its working name, has: its Developer menu started the three lab tools. It has not scanned a sensor yet. Earlier builds have: scans of a loose spare, of the four wheels on the car and of a stored set, and one exit-ship-mode run on the spare. The fix itself was made with the project's lab build, whose transmit code this app uses unchanged.

Part 1 · For car owners

What a tyre pressure sensor does

TPMS stands for tyre pressure monitoring system. Each wheel has a small battery-powered sensor bolted to the back of the valve, inside the tyre. It measures pressure and temperature and sends them to the car by radio. The car shows the result on the dashboard and warns you when a tyre is low.

To save its battery the sensor sleeps most of the time. It wakes when the wheel turns. It can also be woken from outside by a low-frequency radio signal at very short range. That is how a workshop tool reads a sensor while the car is standing still.

The problem: a sensor that never wakes

New sensors leave the factory in a deep sleep called shipping mode, so they do not drain their battery on a shelf. In this mode the sensor ignores the turning wheel. It is fitted, it is healthy, and it says nothing while you drive.

What you see:

  • One wheel shows no pressure on the dashboard, or shows dashes.
  • A TPMS fault or warning light, often some minutes into a drive.
  • The other three wheels read normally.

Why garages need a tool for this

The sensor has to be told to leave shipping mode. The instruction is a specific radio message on 125 kHz, sent from a few centimetres away. Workshop TPMS tools can do it; one maker's menu calls it "Set Sensor to Park Mode". Many cheaper trigger tools can wake a sensor and read it but do not have that function. Ours did not.

The project owner's own estimate for a tool that can do this job is around £1000. That is the cost this project set out to avoid.

What the Flipper does

A Flipper Zero already has both radios the job needs. The coil on its back, normally used for 125 kHz access cards, can send the wake-up and the command. Its Sub-GHz radio can hear the sensor's answer on 433.92 MHz. The app joins the two.

You hold the back of the Flipper against the tyre valve. The app then works in three steps. Select a step to see which parts take part.

Compared with a workshop tool

For this one job the two do the same thing on the air. The differences are in everything else a workshop tool carries.

The app

TPMSFlipper has five entries on its home screen: Scan wheel, Exit ship mode, Live monitor, My wheels and Settings. Screens are shown as the Flipper draws them, 128 by 64 pixels.

Scan wheel

Reads one sensor: pressure, temperature, mode in plain words, sensor ID and signal strength. A second page shows the raw bytes. OK gives the sensor a place: a wheel of a set, the spare tyre or a spare slot. The wake-up reaches every sensor near the coil, and the first to answer is the one read, so with wheels stored side by side a neighbour can answer. Left, Not it, scans again and ignores that sensor and every sensor that already has a place; if no other answers in 84 seconds the app says so, which is also how a flat or missing sensor shows up.

Exit ship mode

The guided fix. It reads the sensor first and stops there if nothing needs fixing. It asks before it sends anything.

Live monitor

Receive only, for use in the car. It shows all four wheels at once with pressure, temperature, the sensor's state (drive, park or ship) and how old each reading is. The car's own display shows pressures only.

My wheels

Keeps track of more than the four wheels on the car. A sensor can be given a place in the Summer set, the Winter set, the spare tyre or one of four spare-sensor slots. Each place keeps what its sensor last told this Flipper and the date, so a set stored in the shed still shows the reading from the day you last scanned it. A setting decides whether a scan is followed by the question "Where is it?".

Settings

Units for pressure and temperature, the set on the car, and whether a scan asks where the sensor is. Radio band chooses what the app listens on: 433.92 MHz for sensors fitted in Europe, 315 MHz for the same sensors as fitted in North America. 315 MHz is untested. Which cars? lists the makes expected to carry this sensor, with a page of models and years for each and how much of that has been tried.

Developer: here be dragons

The last row of Settings. Behind a warning screen are the things a driver fixing a sensor does not need: the switch for a phone link over Bluetooth that is still on test, and three lab tools that the app starts as separate apps (what each does). LF Lab is the bench tool the command was found with, and it sends test frames. Status Watch and Tool Recorder only listen. The tools are optional: a row whose file is not on the SD card says so.

How to use it

What you need

  • A Flipper Zero with a microSD card, on official firmware 1.5.1-rc.
  • The file tpmsflipper.fap from the latest release on GitHub, where the install steps are.
  • A car whose sensors are Continental / VDO TG1C. One car has been tried; which cars use this sensor lists the makes expected to be the same. Sensors fitted in North America send on 315 MHz, not 433.92: Settings > Radio band (untested). See Limits.

Install

  1. Connect the Flipper with qFlipper or the mobile app.
  2. Copy tpmsflipper.fap to SD Card/apps/Sub-GHz/.
  3. On the Flipper open Apps, then Sub-GHz, then TPMSFlipper.

Only for the lab tools: copy the three files in the release's dev folder to SD Card/apps_data/tpmsflipper/dev/. They stay out of the Flipper's Apps menu, and Settings > Developer starts them.

Fix a sensor that is in shipping mode

  1. Find the wheel that is missing on the dashboard.
  2. Choose Exit ship mode. Hold the back of the Flipper flat against the tyre, right at the valve, and press OK.
  3. Read. The app wakes the sensor and shows what it found. If it says PARK MODE and "already OK", this sensor is working and nothing is sent.
  4. Send. If it says SHIP MODE, press OK to confirm. Keep the Flipper still.
  5. Check. The app waits, wakes the sensor again and compares. This can take a minute, because a sensor that has left shipping mode only listens about twice a minute.
  6. Read the verdict, then drive. The car decides whether the fix worked.

Read a wheel, or watch all four

Scan wheel does step 1 on its own and changes nothing. Use it to check a sensor is alive, read its ID, or save it to a wheel position. A sensor in shipping mode answered within a second in our tests. A working sensor listens only every 31 to 33 seconds, so the scan sends the wake-up in 10-second bursts for up to 84 seconds and stops at the first answer.

Live monitor transmits nothing. Leave it running in the car and it fills in each wheel as that sensor reports. It draws the set you have marked as on the car. Sensors it has heard but you have not placed appear in a list, where you can give each a place. Expect gaps: on the one drive logged so far, a Flipper in the cupholder heard seven frames in 15 minutes and one wheel not at all, while the car read all four. A wheel that says "waiting" has not been heard yet. That is the Flipper's reception from inside the car, not a fault.

The app keeps two small files on the SD card under /ext/apps_data/tpmsflipper/: wheels.cfg for your settings and places, and log.csv with one line per scan or fix.

Limits, plainly

What has been shown

  • A Flipper wakes and reads these sensors through the tyre, at the valve.
  • The command frame is acknowledged by two different sensors of the family.
  • On the sensor the car ignored, the status changed to the working sensors' value and stayed there in a second session.
  • On the drive afterwards the car showed a pressure for that wheel and passed its own sensor test (the owner's photos).
  • While driving, the sensors send a different frame, status 66, on their own.
  • The car has kept reading that wheel since, through driving and parking (the owner's report, 23 November 2026).

What has not

  • Any other car, or any other sensor family. One Jaguar XF (X260), one family.
  • Reception on 315 MHz, the band of North American sensors.
  • The lab tools on anyone else's sensors.
  • This app on a sensor in shipping mode. It has scanned sensors on a car, in a stored set and loose, and run its exit-ship-mode sequence on a loose spare that was already working. The fix above used the project's lab build; this app links the same transmit code and sends the same frames.

Safety and the law

  • The 125 kHz signal reaches a few centimetres. It affects the sensor you hold the Flipper against and nothing further away.
  • The command is meant to change a sensor's mode. Use it on your own sensors.
  • The command, like the wake-up, reaches every sensor near the coil, not only the one the app read. Keep other wheels a couple of metres away if you do not want them to receive it.
  • Do not work the Flipper while driving. Start Live monitor before you set off.
  • Radio rules differ between countries. Check yours.
  • No warranty. A TPMS warning can also mean a flat tyre: check pressures with a gauge first.

The LF frame

Both frames the app sends have the same shape: a preamble of 35 on/off pairs, an 18-slot sync pattern (the "9T" pattern from NXP's TPMS reference code), then six data bytes in Manchester code, a 1 sent as on then off. Each frame is preceded by 2.048 ms of plain carrier and followed by an 8 ms gap. Frames repeat for a 10-second burst, about 290 frames, then the app listens for 2 seconds.

The two columns are the same bits with opposite polarity. In each frame the last four bytes are one byte written four ways.

The telemetry frame

The sensor answers with nine bytes. The decoder is derived from the Abarth 124 decoder in rtl_433, which reads the same VDO TG1C telegram.

The status byte

This is the byte that moved. Its first digit says what kind of frame it is and what state the sensor is in, and the app's mode words come from that digit. The words are this project's names for what was observed, not the maker's and not a decode taken from any tool.

  • Bits 6, 5 and 4 cleared together. This run cannot say which of the three is the mode.
  • The low digit follows temperature. A working sensor on this car read 87 at 19 °C in September and 86 at 2 °C in November. The stuck sensor went from F7 to F6 in the cold with nothing sent.
  • Bit 7 is set in every direct reply to a wake and clear in every frame a sensor sent on its own. An observation, not a decoded meaning.
  • The app reads the first digit: 8 PARK MODE, 6 DRIVE, F SHIP MODE, 7 BUSY. Anything else is shown as the byte itself; third-party recordings of another make hold B7, which this project has not placed.

Timing: why a scan can take a minute

A working sensor does not listen for LF all the time. On the bench it checked about once every 31 to 33 seconds, for a fraction of a second. A wake-up burst shorter than that gap can miss the moment entirely, which is why 5-second bursts were unreliable and 10-second bursts repeated a few times are not. The sensor in shipping mode behaved differently: it answered within a second, every time.

How the command was found

It was read out of a workshop tool's firmware update file. Its code holds the wake frame we already used, and next to it a second frame of the same shape. A menu function labelled "DISABLE SHIPPING MODE" sets a flag, and with that flag set the tool sends the second frame in place of the wake.

A forum post from an owner of the same sensor family pointed the way: they had used that function, under a Hyundai menu entry, and a second tool then showed two of their sensors as "Park" where it had shown "Ship". The frame was read from code. It was never captured on air from the tool.

The run at the wheel

12 November 2026, about 2 °C, Flipper held at the rear left valve. Everything on this chart is from the session log.

  • Before. The wake was answered 0.68 s into the burst with status F6, as in the sessions earlier that day.
  • Command. Answered 0.2 s into its first burst. The reply had the same shape as the bench spare's: short groups 1.4 s apart that carried on for nearly six seconds with the LF off. A wake reply stops within 0.3 s of the LF stopping.
  • After. A full 10-second wake got nothing, from a sensor that had answered every wake inside a second until then. The next wake was answered with 86.
  • A minute later. A separate session read 86 again, 31.1 s after the previous reply. That is the working sensors' rhythm.
  • The other wheels. Stock wakes at the three working sensors the same evening all read 86, at 230, 230 and 236 kPa. The stuck sensor read 230 kPa.

Three things changed at once and each now matches a working sensor: the status byte, the answer to a wake, and the listening rhythm. The status byte cannot prove the car's view; only the car can. On the drive that followed, it showed a pressure for that wheel.

On the bench first

Before the wheel, the command was sent to a loose spare sensor that was already in normal mode. It acknowledged with status 77 in four sessions out of four, each time at its next listening moment, and went back to 87 afterwards. That showed the frame is one the family acts on, and that sending it to a normal sensor did no visible harm.

What did not work

The command was found by reading, after weeks of trying to find it by experiment. The dead ends are in the lab notes, which are not published. In short:

  • Changing one bit at a time. All 48 single-bit variants of the wake frame were sent to the spare. None got a reply. The sensor checks every bit, so there is no nearby frame to stumble on.
  • Mixing frames. Bursts that were mostly altered frames with the real wake every few frames showed the sensor examines at least five frames each time it listens. Useful for timing, no new command.
  • The chip maker's bootloader. NXP publishes a bootloader for this class of sensor chip with an LF "connect" message. 57 bursts of it in three forms, over seven sessions, drew no reply. That does not show the sensor has no bootloader.
  • The odd status 77. Seen twice by chance in October and November and chased without success. The spare reports the same status when it acknowledges this command. Whether the earlier sightings had that cause is not known.

Still unknown

  • Whether the change holds over months and long parking. It has held from 12 to 23 November 2026 by the owner's report; nothing was logged in that time.
  • How often a sensor transmits while driving, and what byte 7 carries in those frames.
  • What the mode is called inside the sensor, and which bit of B4 carries it.
  • What 75, 76 and 77 mean beyond "acknowledging".
  • Whether the same frame works on TG1C sensors fitted to other makes. The tool's firmware offers the function for 25 sensor types, which suggests it is not specific to one car.
